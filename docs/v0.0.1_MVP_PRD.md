## **1. Project Background and Objectives**

### **1.1 Background**

Current mainstream IDE AI tools (such as Copilot / Continue) exhibit a structural issue when used with medium to large codebases:

> Responses are non-explainable, non-auditable, and non-reviewable.

Even when an answer *appears* reasonable, engineers cannot determine:

- Which parts of the code the AI based its conclusions on  
- Whether critical paths were missed  
- Whether hallucination occurred  

In high-risk engineering scenarios (refactoring, debugging, understanding legacy code), this significantly undermines engineers’ trust in AI.

Additionally, most mainstream AI code agents today rely on a **remote backend** (e.g., Copilot), which introduces security concerns.

---

### **1.2 Project Goals (MVP)**

CircuitX **does not aim to surpass Copilot in raw intelligence**. Instead, it focuses on solving a smaller, more engineering-oriented problem:

> Making LLM answers in complex codebases *traceable and verifiable*.

The MVP includes only basic Q&A capabilities and **explicitly excludes** Ask-mode (RAG) and code editing features.

---

## **2. MVP Scope and Non-Goals**

### **MVP Goals (Only 4 Things)**

1. VSCode Extension UI (Chat + Sessions list)
2. Configuration management for self-hosted LLM providers (CRUD, persisted to config files)
3. Automatically create a new session upon user query and append all messages to that session
4. Session management (list / view / rename / delete)

### **Non-Goals (Explicitly Out of Scope)**

- ❌ RAG / indexing / embeddings / retrieval  
- ❌ Edit / Patch / Diff  
- ❌ Tool invocation / Agent behavior / multi-step planning  
- ❌ Cost dashboards / observability panels (not in MVP)

---

## **3. Overall Functional Page Structure (Unified View)**

### **Top Toolbar (Globally Consistent)**

From left to right, fix **three icons** (critical for reducing cognitive load):

| **Icon** | **Page** | **Action** |
| --- | --- | --- |
| ➕ | New Session | Return to Welcome page |
| 🕒 | Session History | Navigate to Session History page |
| ⚙️ | LLM Providers | Navigate to Provider Management page |

> ⚠️ Notes:
>
> - **Do not place a “New Session” button on the Chat page**
> - All entry points for creating a new session must be unified as:
>   - The top ➕ button  
>   - The first submission in the Welcome page input box

## **4. Four Functional Pages (Page-by-Page Design)**

---

### **1️⃣ Welcome Page (First Launch & New Session)**

**This is the MVP’s “first impression” page and is critically important**

**Core Goal**

> Allow users to ask questions *without thinking, configuring, or choosing anything*.

**Page Layout**

- Top: CircuitX + toolbar  
- Center:
  - Welcome copy (1–2 lines is sufficient)
  - **One large input box (the only strong interaction)**

**Behavior Rules (Must Be Strictly Enforced)**

- When the user **enters a question and presses Enter**:
  1. Automatically create a new session
  2. Session title = first 30 characters of the question
  3. Navigate to the Active Chat page
- This page **does not display the session list**
- This page **does not display provider switching** (to reduce initial cognitive load)

### **2️⃣ Active Session (Chat Page)**

**Core Goal**

> Keep the user focused on *the current conversation*.

**Page Layout**

- Left: Session list (current + recent)
- Right:
  - Message stream
  - Input box at the bottom

**Key Interactions**

- When sending the first message:
  - If initiated from Welcome → the session already exists
- All subsequent messages are appended to the current session
- Switching sessions from the left list:
  - Immediately updates the message stream on the right

### **Non-Goals (MVP)**

- No multi-tab support for now
- No advanced message operations (edit / retry to be added later)

### **3️⃣ Session History Page**

**Core Goal**

> Allow users to *manage the past*, not chat.

**Page Layout**

- A vertical list
- **Sorted by last updated time (descending)**
- Each item includes:
  - Session title
  - Actions: Edit / Delete

**Behavior Definitions**

- Click a session:
  - Navigate to the Active Session page
- Edit:
  - Rename only
- Delete:
  - Requires confirmation
  - Deletes the session file

> ⚠️ Recommendation: Do not expose Rename / Delete on the Chat page — fully separate “chatting” and “management” mental models.

### **4️⃣ LLM Provider Page**

**Core Goal**

> Make it explicit to engineers which LLM is being used and where it comes from.

**Page Layout**

- Table-based layout (very engineer-friendly):
  - Name
  - Base URL
  - Model
  - Actions
- Bottom: + Add Provider

**Provider Actions**

- Add:
  - Modal or inline form
- Edit:
  - Inline or form-based editing
- Delete:
  - Requires confirmation
- Set Default (recommended via ⭐ or radio button):
  - Used by default for new sessions
